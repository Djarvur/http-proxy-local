# proxy-server Specification

## Purpose

The local proxy server that listens for client requests, serves the generated PAC file at `/proxy.pac`, and cascades all other traffic to the configured upstream proxy. This capability covers binding, PAC serving, upstream forwarding (plain HTTP and CONNECT), basic auth, hot-reload of upstream settings, and the localhost-only deployment posture.

## Requirements

### Requirement: Listen on a configurable local address

The proxy server SHALL listen on a TCP address taken from the live configuration (`listen` field). The default value SHALL be `127.0.0.1:8080`. The server SHALL bind only to the configured address and SHALL NOT bind to wildcard interfaces unless the operator explicitly configures one. The server SHALL apply the current address at startup; subsequent changes to the `listen` field via hot-reload SHALL require a process restart (binding a new listener mid-flight is out of scope for v1) and the server SHALL log an error if `listen` changes on a running process without taking effect.

#### Scenario: Default listen address
- **WHEN** the configuration omits the `listen` field or sets it to empty
- **THEN** the server SHALL bind to `127.0.0.1:8080`

#### Scenario: Custom listen address
- **WHEN** the configuration sets `listen` to `127.0.0.1:9090`
- **THEN** the server SHALL bind to `127.0.0.1:9090`

#### Scenario: listen field changed on a running process
- **WHEN** the `listen` field is edited in config while the server is running
- **THEN** the server SHALL log an error explaining that a restart is required to apply the new listen address
- **AND** the server SHALL continue serving on the previously bound address

### Requirement: Serve the PAC file at a fixed path

The proxy server SHALL respond to `GET /proxy.pac` with the generated PAC document. The response SHALL have HTTP status 200, `Content-Type: application/x-ns-proxy-autoconfig`, and a body equal to the current PAC bytes from the live PAC snapshot. The path `/proxy.pac` SHALL be the only PAC-serving path and is not configurable.

#### Scenario: PAC request
- **WHEN** a client sends `GET /proxy.pac`
- **THEN** the server SHALL return status 200
- **AND** the `Content-Type` header SHALL be `application/x-ns-proxy-autoconfig`
- **AND** the body SHALL equal the current PAC snapshot bytes

#### Scenario: PAC served with post-reload bytes
- **WHEN** the PAC snapshot has been regenerated due to a config or geo-data change
- **AND** a client sends `GET /proxy.pac`
- **THEN** the server SHALL return the regenerated bytes (not a stale copy)

### Requirement: Cascade all non-PAC requests to the upstream proxy

For every HTTP request whose path is not `/proxy.pac`, the proxy server SHALL forward the request to the configured upstream proxy (`upstream.url`). The upstream URL scheme SHALL be either `http` or `https`. The proxy server SHALL preserve the request method, target URL, headers, and body when forwarding. The proxy server SHALL support both plain-HTTP requests (absolute-URI form per RFC 7230 §5.3.2) and `CONNECT` requests (for HTTPS tunneling). Response status, headers, and body from the upstream SHALL be relayed back to the client unchanged.

#### Scenario: Plain HTTP request forwarded to upstream
- **WHEN** a client sends `GET http://example.com/path` to the proxy
- **THEN** the proxy SHALL forward the request to the configured upstream
- **AND** SHALL preserve the method, target URL, headers, and body
- **AND** SHALL relay the upstream's response status, headers, and body to the client unchanged

#### Scenario: HTTPS CONNECT request forwarded to upstream
- **WHEN** a client sends `CONNECT example.com:443` to the proxy
- **THEN** the proxy SHALL establish a tunnel via the configured upstream
- **AND** SHALL bidirectionally copy bytes between client and upstream until either side closes

#### Scenario: HTTPS upstream scheme
- **WHEN** `upstream.url` uses the `https` scheme
- **THEN** the proxy SHALL connect to the upstream over TLS
- **AND** SHALL verify the upstream's TLS certificate

### Requirement: Apply basic auth to the upstream when configured

When `upstream.username` and `upstream.password` are both non-empty, the proxy server SHALL add an `Authorization: Basic <credentials>` header to every request forwarded to the upstream, where `<credentials>` is the base64 encoding of `username:password`. When either field is empty, no `Authorization` header SHALL be added by the proxy (an existing client-supplied `Proxy-Authorization` is forwarded unchanged).

#### Scenario: Basic auth credentials configured
- **WHEN** `upstream.username` is `user` and `upstream.password` is `pass`
- **THEN** every forwarded request to the upstream SHALL include `Authorization: Basic <base64("user:pass")>`

#### Scenario: No credentials configured
- **WHEN** `upstream.username` is empty OR `upstream.password` is empty
- **THEN** the proxy SHALL NOT add any `Authorization` header
- **AND** SHALL forward any client-supplied `Proxy-Authorization` header unchanged

### Requirement: Apply upstream changes from hot-reload without restart

When the live configuration's `upstream` block changes (url, username, or password), the proxy server SHALL apply the new values to all subsequently forwarded requests without a process restart. In-flight requests SHALL complete using the upstream configuration they started with.

#### Scenario: Upstream URL changed
- **WHEN** `upstream.url` is changed in config while the server is running
- **THEN** the next forwarded request SHALL use the new upstream URL
- **AND** any in-flight request SHALL complete on the previous upstream

#### Scenario: Upstream credentials changed
- **WHEN** `upstream.username` or `upstream.password` changes while the server is running
- **THEN** the next forwarded request SHALL carry the new `Authorization` header

### Requirement: Localhost-only, unauthenticated

The proxy server SHALL NOT require authentication from its clients and SHALL NOT implement any client-facing auth mechanism. The default bind address (`127.0.0.1`) ensures the proxy is reachable only from the local machine; this is the intended deployment posture and is not a deficiency.

#### Scenario: No client auth
- **WHEN** any client connects to the proxy
- **THEN** the proxy SHALL serve requests without requiring credentials
